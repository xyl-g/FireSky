# macOS 产品与 UI 基准

更新日期：2026-11-24。依据用户明确决定：**以 macOS 为基准，其他 UI 最终向 macOS 对齐**。
本文定义产品与界面的对齐方向；最新 UX 改造与验收记录见[macOS Liquid Glass 交接规范](MACOS_LIQUID_GLASS_UX_HANDOFF.zh-CN.md)与[macOS 界面图册](ui/macos/README.md)。

## 1. 基准与对齐方向

- `apps/macos/` 的 SwiftUI/AppKit + Rust FFI 是当前优先完善和验收的产品端。
  先稳定 macOS 的工作流程、信息层级、图表/地图语义及异常状态，再形成可复核的基准。
- 共享 Web、未来 Windows/Linux UI 均以验收后的 macOS 为目标。旧 Web/Qt 用于核对
  历史能力和用户数据迁移；已有能力差异先登记，再按 macOS 产品需求决定保留、迁移或退役。
- macOS 当前代码中的缺陷、占位值和未验收行为不能直接成为规范。基准由用户决定、
  实际 Rust 数据合同和通过验收的 macOS 行为共同确定。
- 各端统一功能、数据口径、工作流程、信息层级和状态反馈；导航、控件、系统菜单、
  文件操作与辅助功能按各自平台实现。跨端对齐不要求逐像素复制或复用 SwiftUI 代码。
- 所有端消费同一套 Rust 业务能力；评分、时次选择、预检、准备、任务/取消和来源身份
  由 Rust 负责。UI 不另写科学算法或以另一端的值补齐本端缺测。

## 2. 当前优先级

1. 完善并验收 macOS 的点预测、区域预测、实况、数据/设置、历史恢复等日常流程。
2. 修复影响上述流程的共享 Rust 问题，完成 macOS 真实数据、性能与安装包验收。
3. 以已验收 macOS 建立跨端差异矩阵，推进共享 Web 对齐；Windows/Linux 在用户恢复
   平台开发后按同一基准接续。
4. Docker 的页面路径、镜像构建和部署门禁归入后续 Web 交付；保留已发现缺陷及验收要求，
   不作为当前 macOS 工作的前置门槛。

## 3. macOS 基准覆盖面

以下是待建立证据的基准范围，不表示所有项目已经验收通过。

| 页面/流程 | 基准应明确的内容 | 验收证据 |
| --- | --- | --- |
| 点预测 | 位置/海拔/时区/日期/朝晚霞；GFS/EC 独立摘要；质量与推荐窗口；评分组成、趋势、台账、剖面和来源说明 | 同一输入下的操作记录、结果 JSON、各结果页截图及缺测/单模式失败状态 |
| 区域预测 | 预设/自定义区域；质量地图、固定色带、覆盖/缺测、模式比较、网格/城市排行、详情和冻结剖面查询 | 真实地图渲染截图、网格/城市详情对照、跨线场景独立验收 |
| 实况 | 卫星帧时次与覆盖、质量趋势、云况/运动/光学与雷达、冻结概率剖面、来源时效及不可用原因 | 同 fixture 读数、至少两帧真实输入工作流、未知/覆盖不足/缺数状态 |
| 数据与设置 | 本地库存与请求 readiness 的区别；显式下载探测；ADS/EC 来源设置；同步与保留设置；进度/取消/失败 | 设置持久化、同步状态与任务历史、脱敏错误、取消后缓存和历史结果状态 |
| 预检与任务 | 检查、准备、确认、计算、取消、失败、重试及服务重启后的状态反馈 | 完整流程走查、引擎事件与 UI 状态对照；单次确认与实际来源一致 |
| 历史恢复 | 不可变结果快照恢复、缺失/篡改/过期原因、重试重新预检；冻结剖面有独立寿命 | 新包重启恢复、原始缓存淘汰后结果读取、过期剖面提示 |
| 应用体验 | 导航与结果页层级、窗口缩放、浅深色、长标签、键盘焦点、VoiceOver、旧配置导入 | 1440×900、1120×720、窄窗口截图及键盘/VoiceOver/迁移记录 |

## 4. 已确认的展示与行为规则

- GFS/EC 独立显示，不平均、不跨模式填补失败。质量固定 0–2.5；比例与 AOD 使用明确单位和独立量纲。
- 区域结果必须在地图渲染，列表不替代地图；缺测不填零、不参与有效排行。
- 模式单点不增加预测云场地图；位置选择地图保留。地图与图表不要求联动；实况地图继续单独立项。
- 没有真实输入的指标显示缺测、未计算或未接入，明确来源/周期/有效时间；不把置信度占位值解释成命中概率。
- 预测前预检按本次请求验证科学字段、空间和时间覆盖；库存数量和已保存凭据不能当作准备成功。
- 失败和取消不覆盖上一份有效结果。任务重启后中断，按现有合同由用户重试，不静默重新下载或计算。
- 模式后台同步默认关闭，启用后按已有设置与生命周期合同执行；卫星保持按实况请求准备。
- 结果恢复与短期计算缓存分开；冻结剖面源过期时如实提示，不因结果可恢复而承诺无限期重新计算。

## 5. 建立与更新基准

先从当前源码重新构建 macOS 应用，记录源码/引擎 `source_id` 与包身份。用已有缓存或 fixture
走查全部主要页面，修复实际影响使用的缺口，保存截图、结果 JSON 和状态记录；随后补真实数据
和安装包验收。fixture 验证、真实输入验证、辅助功能与发布验证分别记录。

每份基准证据记录页面/场景、输入与时间来源、窗口/主题、实际读数、预期状态、证据路径及未通过项。
基准修订先在 macOS 验证，随后更新跨端矩阵；共享 Rust 合同变更同步列出所有受影响消费者。

## 6. 其他 UI 如何对齐

以 macOS 的主要页面和用户操作为行，分别为 `apps/shared-web/`、旧 `frontend/`、
Windows 和 Linux 登记：macOS 基准行为、现有行为、差异、所需接口/平台适配、状态和证据。
状态使用“已对齐 / 待对齐 / 平台适配 / 暂停 / 已决定不支持”，不把缺失能力写成完成。

Web 的工作台、摘要、图表/地图、逐时台账、数据与任务页按 macOS 的产品层级收敛。
浏览器无法直接承担本机目录、Keychain 或应用退出等系统能力时，使用适当的浏览器等价行为
或明确不可用；不能把服务器本地路径暴露为用户文件操作。

旧 Web 独占的 admin、鉴权、SSE 等部署管理能力单独登记其使用场景和保留方式，不强行塞入
macOS 日常预测页面，也不在完成消费者核对前删除。Docker 仅承载 Web/HTTP 部署，其构建
和运行问题在 Web 交付阶段处理。

Windows/Linux/Docker 对齐开发已于 2026-11-14 在 `feat/win-linux-docker-parity`
分支恢复：三端均按本文的 macOS 基准接入（Windows 数据页任务历史/恢复/重查、
Linux 统一预检/任务历史/恢复、Docker/Web 本地构建与运行冒烟）；目标机验收
与后续差异登记见[跨平台基线](NATIVE_UI_CROSS_PLATFORM_BASELINE.zh-CN.md)。
